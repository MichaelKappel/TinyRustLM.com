# vNext Site Publication Materialization

## Scope

`tinyrustlm/tools/vnext-site-publication.js` is the pure, deterministic boundary
between exact static production readback and the later deployment of generated
publication files. Its frozen profile is
`contracts/vnext/site-publication-profile.v1.json`, with SHA-256
`d959ce557e8b18a71514e2388a8eda7162182e38f5febf2e1a39b063fa5ba4bc`.

This module performs no filesystem write, network request, clock read, source
mutation, signing operation, deployment, or receipt persistence. Its outputs
are candidates only. In particular, a successful function return never means
that a site, release, generated file, or claim is public.

## Forward-Only Graph

The publication graph is deliberately acyclic:

1. `release_manifest.v3` binds the static web graph and the exact path, role,
   media type, cache policy, header-profile hash, and generator hash for the two
   generated files. It does not bind generated bytes that must name its own
   final identity.
2. The release-authorized deployment is read back from production. One
   immutable `public-readback` receipt binds the exact static inventory and
   remains explicitly `not-published`.
3. `createVnextSitePublicationPlanMaterial` reconstructs the release, approved
   claims, static readback, optional prior current-vNext history, and generator
   bytes. It returns canonical plan material only.
4. The release surface creates one `site-synchronization` plan receipt over
   that material. A current `site-publisher` signs that receipt with scope
   `site-publication` and the exact release ID.
5. `materializeVnextSitePublication` deterministically derives the pointer,
   append-only history candidate, and direct `published` claim descendants.
   These bytes remain unpersisted and unclaimed.
6. An authorized external deployment operation writes those exact generated
   bytes. The sole production HTTPS verifier reads the bootstrap, pointer, and
   history back and binds exact bytes, headers, origin, and TLS observations.
7. Only after that generated-file readback may the release surface create-only
   persist the published claim descendants and final publication evidence.

The plan receipt, publisher signature, generated documents, generated-file
readback, and final publication receipt point only forward. No manifest,
receipt, claim, pointer, or history document embeds its own future identity.

## Exact Inputs

Plan construction accepts exactly:

- canonical `release_manifest.v3` bytes;
- canonical bytes for every approved claim named by the release, in exact
  release order;
- the canonical static `public-readback` receipt;
- exact publication-generator bytes whose SHA-256 equals the manifest binding;
- either `null` or canonical history from this one current vNext profile.

Materialization accepts those same inputs plus the canonical plan receipt and
canonical site-publisher signature receipt. Hidden fields, symbols, accessors,
sparse arrays, unknown fields, invalid UTF-8, noncanonical JSON, duplicate
members, over-limit bytes, reordered claims, omitted claims, extra claims, and
wrong schemas fail before output construction.

The static readback must be a passing `public-readback` receipt for the same
campaign, source revision, release ID, and public origin. Its evidence scope,
asset count, total bytes, manifest hash, generator hash, security-header hash,
web-asset inventory, verified inventory, and observation-inventory identity
must agree with values independently recomputed from the release.

## Plan Authority

Canonical plan material binds:

- approved claim IDs and their domain-separated set identity;
- campaign, release, source revision, site, and public origin;
- release-manifest canonical-content hash;
- static readback receipt ID;
- current profile ID and exact profile-file SHA-256;
- publication-generator and security-header-profile hashes;
- exact previous-history SHA-256 or `null`;
- a domain-separated materialization seed.

The `site-synchronization` receipt has scope
`site-publication-plan-only`. It uses the static readback as its sole phase
parent, binds the exact material hash and all control hashes, retains the
campaign attestation reference, and carries no security payload. This receipt
cannot establish publication.

The signature receipt must have role `site-publisher`, domain
`tinyrustlm.signature.site-publisher.v1`, scope `site-publication`, signed
schema `receipt.v1`, signed subject equal to the plan receipt, and release ID
equal to the finalized manifest. This pure module validates structural and
temporal binding. The sole release surface remains responsible for
cryptographic verification, current authority-registry reconstruction,
revocation, nonce replay, key status, finite lifetime, and trusted verification
time before invoking materialization.

## Generated Documents

`/.well-known/site-release.json` is canonical JSON with `no-store`. It names
the campaign, product, site, origin, release ID and canonical hash, version,
release date, source revision, publisher-signature receipt, static-readback
receipt, static observation inventory, current profile identity, authorization
time, and exact published-claim descendant IDs.

`/.well-known/site-release-history.json` is canonical JSON with `no-store`.
Its entries are strictly append-only and strictly increasing by publisher
authorization instant and SemVer precedence. Release IDs may not repeat and
release dates may not go backward. `generatedAtUtc` equals the last entry's
authorization instant.

Only history from this exact profile ID and profile SHA-256 is accepted. The
old release-ledger schema is rejected. There is no alias, converter, migration
shim, dual reader, or fallback. Historical old-format receipts remain audit
evidence outside the current product path.

## Published Claim Descendants

Each generated claim:

- retains subject, site, route, component, wording class, claim type, evidence
  tier, scope, wording, owner, redaction, review time, and expiry;
- changes status to `published`;
- binds the exact release ID;
- retains prior evidence and adds the static-readback and site-publisher
  signature receipts;
- sets effective and last-verified time to publisher authorization time;
- has no blocker;
- directly supersedes exactly its approved parent.

Publisher authorization at or after claim review or expiry fails closed. The
claim bytes are materialized before generated-file readback to keep the pointer
identity acyclic, but they are not persisted until that readback succeeds.

## Output Ownership And Limits

All outputs are RFC 8785 JCS bytes under the profile's safe-integer limits.
The wrapper and metadata are deeply frozen. Every byte getter returns a new
owned copy so caller mutation cannot change retained evidence. Input aggregate,
claim, pointer, history, entry-count, and generated-total limits are enforced
before an output is accepted.

The generated inventory domain-separates exact path, role, length, SHA-256,
media type, cache policy, and security-header-profile hash. The published-claim
set likewise binds each claim ID and canonical-content hash.

## Release-Surface Integration And Non-Claims

The focused conformance suite passes deterministic replay, defensive ownership,
strict two-release history append, old-schema and noncanonical rejection,
selection and binding drift, wrong plan/signature release, claim expiry,
hostile accessors, and resource limits. Those tests are local fixture evidence.

The sole release surface now reconstructs the exact static-readback closure,
create-only persists the redacted plan lineage, verifies one current
site-publisher Ed25519 authority graph, invokes this materializer, and scans the
signature plus every generated control and claim candidate. Its conformance
test also proves byte-identical plan and authorization replay, rejects caller
publication truth, and rejects the publisher signature at expiry.

This checkpoint still does not prove generated-file deployment, generated
production readback, claim persistence, final release publication,
source-control publication, or any `20/50/25/40/20` campaign counter. Those
remaining operations must stay inside the sole release surface, retain
create-only persistence and exact restart recovery, and admit pointer, history,
and published-claim descendants only after exact deployed-byte readback.
