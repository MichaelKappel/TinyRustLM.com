# **Fifty-Round Fresh-Browser Dogfood Harness And Conversation UX Reliability**

## **1\. Public TinyRustLM Observation Log**

The public observation of the TinyRustLM architecture, conducted on July 14, 2026, against the deployed artifact at GGUF.MiRust.com and TinyRustLM.com, establishes the baseline for the browser-automation harness. The interface was evaluated across a strict viewport matrix comprising desktop dimensions at 1920 by 1080 pixels, narrow desktop dimensions at 1024 by 768 pixels, and mobile dimensions at 375 by 812 pixels. The architectural reality of the application differs significantly from conventional remote-inference web clients, necessitating a highly specialized reliability engineering approach.
The observed application operates exclusively through a 114 KiB WebAssembly (WASM) module compiled from a zero-dependency Rust workspace1. This module exposes a raw C-style application binary interface (ABI) that manages model loading, memory allocation, and token generation directly on the browser's main thread, completely lacking Web Worker delegation, WebGPU acceleration, or background thread pools1. The system enforces a strict 128 MiB single-transfer ceiling for memory allocation, requiring the entire model artifact to be copied into a contiguous WASM memory block prior to initialization2.
Furthermore, despite the project's domain nomenclature, the active runtime contains no GGUF loader; it exclusively parses a custom .slm v1 binary container1. This format is characterized by a 108-byte header, 64-byte aligned tensor directory entries, and an embedded internal tokenizer utilizing either BPE1 or BTOK algorithms1. The memory footprint is statically bound to mathematical formulas derived from the artifact dimensions, requiring equal counts for attention and key-value heads, which inherently rejects Grouped-Query Attention (GQA) and Multi-Query Attention (MQA) architectures1. Network activity is restricted to fetching loopback static assets, ensuring that model bytes remain strictly local or operate via direct peer-to-peer protocols without exposing proprietary prompts or weights to external ingestion endpoints.

## **2\. Campaign Manifest and State Machine**

To produce statistically significant evidence regarding user experience reliability and memory continuity, the dogfood campaign must execute precisely 50 complete rounds. This execution is orchestrated by a cryptographically secured campaign manifest that defines the exact state machine, binds the application origin, and schedules the randomized yet strictly distributed evaluation matrix.
The campaign manifest operates as an immutable JSON ledger binding the overarching campaign ID to exactly 20 cryptographically distinct, quality-qualified .slm artifacts. The schedule guarantees that every model is exercised in at least two independent, clean-profile restarts, satisfying 40 of the required rounds. The remaining 10 rounds are distributed among the heaviest models in the manifest to induce maximal memory pressure on the WASM allocator. The manifest dictates the prompts by private hash rather than plaintext, ensuring that the automation harness does not inadvertently leak intellectual property into system logs if a crash occurs. Exactly 25 of these 50 rounds are explicitly designated for memory-continuity testing, requiring the state to be synchronized through the MultiAgentMemory MATM protocol at MemoryEndpoints.com.
Model aliases or duplicate bytes are universally rejected during the manifest validation phase. This cryptographic enforcement is critical to prevent the automation harness from spoofing a legitimate conversation round by repeatedly loading the documented 4.8 KiB or 8.6 KiB deterministic runtime smoke fixtures3. A fixture of this size fails to stress the 128 MiB transfer ceiling, circumvents the mathematical limits of the forward scratch buffer, and is fundamentally incapable of generating genuine multi-turn conversational syntax2. By demanding 20 distinct, verified models in f32, q8\_0, or q4\_0 formats, the campaign guarantees that the browser process experiences realistic memory fragmentation, tensor materialization delays, and garbage collection pressure1.
The orchestrator transitions through a rigid state machine for each round. The sequence begins with the preparation phase, verifying the manifest and local file hashes. It advances to profile initialization, generating an isolated directory root on the host filesystem. The execution phase manages the file injection, multi-turn conversation, and visual assertions. If the round is flagged for memory continuity, the machine branches into the sync phase, awaiting the immutable revision receipt from the external endpoint before proceeding to the teardown phase.

## **3\. Fresh-Profile and Deletion Protocol**

Achieving a verifiably clean browser state on every round requires abandoning superficial isolation methods. The campaign strictly prohibits the use of localStorage.clear(), simple page reloads, or Playwright's browser.newContext() for data restarts, as these methods fail to guarantee the erasure of orphaned IndexedDB structures, persistent service-worker caches, or network-level isolation keys4. The only acceptable method is the creation and subsequent physical deletion of an owned, fresh user profile directory.
Every round initiates a browser session utilizing the chromium.launchPersistentContext(userDataDir) method6. The orchestrator asserts safe temporary-root ownership by dynamically generating a highly entropic path within the operating system's temporary directory, prefixed specifically for the campaign. This ensures that the headless browser instance constructs an entirely new set of SQLite databases for cookies, local storage, and profile preferences without inheriting state from previous test executions or the host machine's default user profile.
The teardown and deletion phase is notoriously complex due to operating system filesystem locks. On Linux, Chromium utilizes a ProcessSingleton lock, while Windows environments frequently retain file handles on the userDataDir even after the primary process signals termination8. A naive deletion command will result in an EBUSY error on Windows or leave zombie instances in the background on Linux, corrupting subsequent runs9. Process closure is managed by explicitly awaiting the closure of all pages, followed by the context, and finally the browser instance, forcing the underlying databases to flush their write-ahead logs4.
Profile deletion incorporates an exponential backoff retry mechanism. If the operating system rejects the initial deletion request, the orchestrator pauses and retries up to five times to allow lagging kernel file handles to release10. To make recursive deletion impossible outside the owned root, the teardown function programmatically verifies that the absolute path strictly begins with the expected temporary prefix and explicitly rejects paths resolving to root directories, user home directories, or system folders. Proof of deletion is ultimately asserted by confirming the directory no longer exists on the disk before the state machine permits the commencement of the next round.

## **4\. Real-Model Import and Conversation Procedure**

The ingestion of large local models into the browser context represents a significant reliability hurdle, particularly because typical automation protocols impose payload limitations. The Playwright Model Context Protocol (MCP), for instance, enforces a 50 MiB upload limit for files transferred over the bridge12. To bypass these restrictions and simulate true user interaction, the campaign relies on the native FileChooser API to select large local .slm files13.
The orchestrator executes a trusted click on the interface's upload button concurrently with page.waitForEvent('filechooser'), allowing the harness to intercept the OS-level dialog and programmatically invoke setFiles() with the absolute path of the target model13. Following the file selection, the WASM and native load status are deeply monitored. The system tracks the 108-byte header validation, the decoding of the 64-byte tensor directory entries, and the custom non-cryptographic checksum verification1. Strict timeout budgets are enforced during this phase; the allocation of the forward scratch and KV cache must complete within fifteen seconds, or the round is flagged as a failure due to memory pressure or a WASM Out-Of-Memory (OOM) trap1.
Once the model transitions to the ready state, the conversation execution mandates a genuine multi-turn interaction spanning two to six specific turns. This matrix requires the model to navigate casual chat to establish basic attention, ambiguity to evaluate response branching, practical planning to stress sequential reasoning, source conflict to test context window retention and contradiction checking, current preference tracking, untrusted memory handling, summarization, rewriting, structured output generation, and finally, code formatting. A single prompt is entirely insufficient to validate the KV cache's durability across the generation transaction1.
During this execution, the automation preserves the raw model output while enforcing strict user interface contracts. Mutation observers are deployed to guarantee that each assistant answer renders exactly once on the DOM, preventing bugs where the streaming decoder duplicates assistant text blocks. The orchestrator asserts scroll stability by calculating bounding boxes, ensuring the viewport remains anchored to the active generation node without chaotic jumping. Furthermore, cancellation behavior is evaluated by interrupting the generation mid-stream, proving that the WASM state safely resets and the tokenizer clears the transient arrays without leaking handles or causing a main-thread panic1.

## **5\. Browser Restart Semantics**

Differentiating between superficial state resets and genuine cryptographic isolation is a core tenant of the campaign's reliability engineering. The framework strictly delineates between a page reload, a context reset, a browser restart, and an actual persistent-profile deletion.
A page reload preserves all disk-backed storage, IndexedDB tables, and active Service Worker registrations, making it entirely unsuitable for isolation testing15. A context reset clears in-memory cookies but leaves the underlying persistent profile databases completely intact4. A standard browser restart flushes memory but reconnects to the existing userDataDir, recovering the previous session's storage7. Therefore, a true data restart can only be achieved by executing the full process closure, verifying that no zombie handles remain, and completely deleting the physical directory from the filesystem9.
For the 25 rounds designated for memory continuity, the restart semantics are uniquely complex. At the conclusion of the conversation, the first browser process is cleanly closed and its profile deleted. The orchestrator then creates a second, entirely distinct fresh profile with a new temporary directory7. This forces the application to boot into an environment utterly devoid of local storage, cookies, or cached tensor fragments. It proves that the subsequent restoration of the conversational state relies exclusively on the successful retrieval of data through the MultiAgentMemory MATM protocol, rather than relying on lingering local artifacts17. Once the continuity verification is complete, this second profile is also subjected to the strict deletion protocol.

## **6\. Secret and Privacy Scanning Contract**

The architecture of modern browser storage partitioning—such as Mozilla's Total Cookie Protection (TCP) and Chrome's Cookies Having Independent Partitioned State (CHIPS)—double-keys client-side state based on both the origin of the resource and the top-level site18. The campaign leverages an understanding of these boundaries to execute a comprehensive secret and privacy scanning contract before any profile is deleted.
The automation injects an evaluation script into the page context to scrape and serialize all local storage mediums. Because IndexedDB data does not update synchronously in external observation tools, the script utilizes page.evaluate() routines to interact directly with the database cursors, pulling ArrayBuffers and Blob data from the object stores22. The scanner also intercepts Cache Storage, Service Worker states, localStorage, sessionStorage, and examines Playwright network traces16.
This serialized output is subjected to heuristic decoding, accounting for UTF-8, UTF-16, Base64 encodings, and compressed payloads2. The contract mandates an immediate, unrecoverable campaign failure if any sensitive data is discovered in unencrypted, persistent layers. This includes enrollment URLs, raw agent tokens, workspace bearer keys, user prompts, or local model bytes17. The scanning logic is designed to mitigate false alarms from legitimately hashed values, such as the FNV-1a name hashes utilized within the SLM1 tensor directory or the SHA-256 base hashes used for local collaboration overlays, by verifying payload lengths, entropy signatures, and structural context1.

## **7\. Network Assertions**

The campaign operates under a zero-trust network policy enforced via Playwright's route interception capabilities (browserContext.route())4. The network contract permits only a strictly defined allowlist of outbound and inbound requests.
The orchestrator permits expected public static assets required for the application shell, catalog metadata for discovery, direct peer-to-peer loopback traffic for companion synchronization, and the specific MemoryEndpoints MATM API operations required for the 25 continuity rounds17. Any deviation from this allowlist triggers an immediate round failure. The harness explicitly monitors for, and blocks, unauthorized prompt uploads to project sites, implicit telemetry gathering, public requests for model bytes, and any credential-bearing URLs attempting to pass workspace keys via query parameters rather than secure headers17. By isolating the network, the campaign guarantees that the TinyRustLM execution remains fundamentally local and private.

## **8\. UI Verification at Desktop, Narrow Desktop, and Mobile Widths**

Functional fixes and optimizations to the WASM runtime or memory allocator must not casually redesign or break the approved user interface. The visual language of the application is locked, and the campaign verifies this stability across desktop, narrow desktop, and mobile viewports.
Instead of relying on fragile CSS selectors or inconsistent pixel-matching algorithms, the automation heavily utilizes Playwright's accessibility tree snapshots (page.ariaSnapshot()) to guarantee semantic integrity25. The orchestrator verifies that introductory prompt cards, identified by specific ARIA roles, are fully visible upon initial load but completely disappear from the accessibility tree the moment the chat sequence is initiated25. The center column is asserted to become the primary, expansive conversation workspace.
Responsive checks ensure that overlapping columns do not obscure text on narrow viewports and that the fixed composer behavior remains anchored, allowing the user to type without the input field scrolling off-screen or being occluded by mobile virtual keyboards. Long names and extended unstructured output must wrap correctly without breaking the flexbox boundaries. Furthermore, keyboard navigation is tested by injecting tab-key progressions to ensure all interactive elements remain reachable, and screen-reader labels are validated for accuracy. The harness also injects an emulation state for reduced motion (emulateMedia({ reducedMotion: 'reduce' })) to guarantee compliance with accessibility standards. Crucially, any screenshots taken by the harness for diagnostic purposes are subjected to automated redaction to ensure they do not contain secret bearer tokens, private prompts, or sensitive MATM routing decisions17.

## **9\. Durable, Resumable Receipts**

The output of the dogfood campaign is a cryptographic ledger composed of durable, resumable receipts. This schema provides the incontrovertible evidence required to support or reject product claims regarding the TinyRustLM architecture.
The receipt schema is structured as an immutable JSON document capturing the campaign hash, the unique round identifier, the precise model identity (SHA-256), the exact Chromium browser build version, the evaluator's cryptographic signature, and a detailed array of evidence fields encompassing DOM mutations, peak memory allocations, and network intercept summaries.
A resume algorithm is implemented to handle environmental interruptions, such as simulated power loss or host operating system crashes. A completed round is idempotently resumable only when all validation points—the campaign hash, model identities, browser build, and evaluator signature—strictly match the existing ledger. Failed rounds, whether due to a WASM trap or a secret-scanning violation, may be retried according to the configuration matrix, but their original failure receipts cannot be overwritten or silently converted into passes11. This design mirrors the Idempotency-Key and immutable revision strategies of the MATM API, ensuring that the history of errors, retries, and eventual successes is preserved transparently for architectural review17.

## **10\. Resource Budget and Execution Schedule**

Managing 50 complete rounds, particularly when each utilizes large local models up to 128 MiB in size, requires a highly disciplined resource and scheduling strategy. Because the current TinyRustLM implementation executes inference synchronously on the browser's main thread without Web Worker delegation, CPU starvation and memory fragmentation are critical risks1.

| Resource Category | Budget Constraints & Formulas |
| :---- | :---- |
| **Disk Storage** | 2.56 GiB for 20 models \+ \~150 MiB per active userDataDir. |
| **RAM / Process** | Chromium overhead (\~250 MiB) \+ WASM execution limits. |
| **WASM Memory** | Host Transfer (Max 128 MiB) \+ Forward Scratch (![][image1]) \+ KV Cache (![][image2]) \+ Logits (![][image3])1. |
| **Peak Active Memory** | Hard cap at 1.2 GiB per round to prevent browser tab termination. |
| **CPU Time / Timeout** | 120 seconds maximum per 6-turn conversational round. |

The campaign enforces a strict serial execution policy for the core conversation generation phases. While Playwright readily supports parallel test workers27, executing multiple main-thread WASM inference loops simultaneously on a single host machine results in severe CPU bottlenecking, thermal throttling, and artificial timeout failures that do not reflect genuine user experience. Parallelism is permitted exclusively during the teardown, network validation, and profile initialization stages, optimizing the overall schedule while protecting the integrity of the synchronous generation transaction.

## **11\. Fault-Injection Matrix with Expected Evidence**

A robust reliability campaign does not merely test the happy path; it actively introduces hostile conditions to validate the architecture's recovery transitions and error diagnostic capabilities2. The orchestrator injects 13 specific faults during designated rounds to observe the system's resilience.

| Injected Fault | Execution Phase | Expected Evidence & Recovery Transition |
| :---- | :---- | :---- |
| **Browser Crash** | Generation | userDataDir retains SQLite/IndexedDB state; subsequent launch detects partial state; MATM sync engine safely rejects stale parents17. |
| **Power Loss** | File Import | Transaction is interrupted before tensor materialization. Resumption algorithm re-runs the round from a clean state. |
| **Model Corruption** | Import | Rust parser validates the 108-byte header and custom checksum1. Fails safely without a WASM trap, emitting a stable numeric error code2. |
| **WASM Trap (OOM)** | KV Allocation | Exceeding the mathematical boundary triggers a safe JavaScript catch. UI renders a stable error message without crashing the tab1. |
| **Generation Timeout** | Decoding | The autoregressive loop is forcibly cancelled. State reverts safely; memory handles do not leak into the global mutex1. |
| **Network Loss** | Memory Continuity | Route interception drops packets. The MATM /api/matm/memory-events/submit fails17. UI queues the mutation; IndexedDB holds the pending sync. |
| **P2P Peer Loss** | Sub-routine | Companion connection drops. System gracefully falls back to isolated local state without hanging the main thread. |
| **Companion Restart** | Validation | Loopback traffic restarts. Session reconnects automatically without losing the active conversation context. |
| **IndexedDB Failure** | Pre-computation | Database forced into read-only mode via DevTools protocol. Application must disclose the storage error visually. |
| **Locked Profile** | Teardown | SingletonLock remains active post-closure9. Orchestrator triggers the 5-attempt retry backoff10; logs a filesystem warning. |
| **Stale Service Worker** | Page Reload | testOptions.serviceWorkers behavior audited24. Cache Storage ignores the network payload, serving the app shell offline successfully16. |
| **Duplicate Response** | Resumption | Idempotency key conflict simulated17. MATM API returns a conflict-safe 409 or no-op17. UI renders exactly one authoritative transcript. |
| **Restore Conflict** | Sync | Simulated out-of-order epoch17. System requests manual intervention or forces a fresh synchronization pull. |

## **12\. Acceptance Report Format and Blocker Taxonomy**

Upon conclusion of the 50 rounds, the campaign generates a comprehensive JSON acceptance report alongside a human-readable summary. Anomalies are classified according to a strict taxonomy aligned with the project's evidence gates1:

* **Blockers (Severity 1):** Unrecoverable failures that immediately halt promotion. These include cryptographic hash mismatches during model admission, main-thread panics causing the browser tab to crash, secret-scanning violations (e.g., leaked workspace keys in logs), attempted recursive deletions outside the temporary root, and explicit telemetry or network violations.
* **Critical (Severity 2):** Severe UX degradations. These include duplicate assistant text rendering, failure to accurately reconstruct MATM state in the secondary fresh profile, or memory leaks that cause the process to exceed the 1.2 GiB RAM budget over successive turns.
* **Warnings (Severity 3):** Manageable friction points. These include the Playwright SingletonLock requiring more than two deletion retries, minor layout shifts on mobile viewports, or delayed screen-reader announcements during WASM execution.

Progression from experimental deployment to stable support requires an acceptance report containing zero Blockers and zero Criticals.

## **13\. Unknown Local Facts**

The campaign operates with several localized variables that the orchestrator must dynamically account for during execution. Operating system sandboxing represents a major unknown; differences between Linux AppArmor, SELinux, and Windows Defender Application Control (WDAC) can significantly interfere with Playwright's executable caching and local memory mapping, occasionally requiring specific kernel-level whitelisting to prevent the userDataDir from locking28. Hardware concurrency is another variable; because the current WASM module lacks threading, inference speeds will fluctuate wildly depending on the host machine's specific single-core IPC (Instructions Per Clock) and L3 cache latency1. Finally, filesystem latency heavily influences the speed of profile creation and recursive deletion, making the exponential backoff retry loop a necessity rather than a precaution across diverse NVMe and SATA SSD hardware environments.
