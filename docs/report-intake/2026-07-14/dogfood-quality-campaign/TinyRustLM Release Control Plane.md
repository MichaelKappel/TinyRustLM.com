# **End-To-End Campaign Evidence, Release Gates, and Failure-Driven Operations**

## **1\. Executive Control-Plane Recommendation**

The successful execution, validation, and publication of the TinyRustLM intelligence campaign demands a fundamental departure from traditional continuous integration pipelines. A campaign that rigorously qualifies 20 distinct models, executes 50 clean-browser conversations, performs 25 live MemoryEndpoints continuity runs, and guarantees publication across two externally proven peer-to-peer (P2P) lanes cannot rely on ephemeral build environments or binary pass/fail assertions. The architectural recommendation is to implement an immutable, evidence-driven control plane governed strictly by a content-addressed Directed Acyclic Graph (DAG) of cryptographic receipts.
Traditional boolean status flags are inherently fragile because they fail to capture the context, tool versions, and environmental variables present at the exact moment of execution. This control plane rejects the concept of a boolean completion state. Instead, progression through the campaign is achieved exclusively through the atomic generation of structured evidence. Partial success is treated as a highly valuable diagnostic artifact, generating permanent error receipts rather than evaporating into standard output logs. Furthermore, external blockages—such as rate limits on the MultiAgentMemory endpoints, absent P2P peers, or pending human authorization—are recorded explicitly as distinct, persistent states. They are never masked as skipped tests or simulated passes.
This architecture must successfully navigate constraints spanning multiple distinct operational domains. First, the TinyRustLM runtime is strictly bounded; it operates as a single global runtime serialized by a mutex, constrained to scalar CPU execution on the main browser thread, and subject to a rigid 128 MiB host transfer ceiling1. Second, the MemoryEndpoints system enforces a zero-trust tenancy boundary, requiring precise Idempotency-Key orchestration and hash-only local .uai collaboration heads to coordinate state without persisting tenant payloads on the server2. Third, the dual-lane P2P requirement necessitates the integration of both the BitTorrent protocol—utilizing the Mainline DHT and rarest-first piece selection3—and the libp2p networking stack, which introduces Noise protocol encryption, Multiaddr conventions, and Kademlia routing5. Finally, the deployment tier must adhere strictly to Supply-chain Levels for Software Artifacts (SLSA) Level 3 provenance protocols8, combining Cargo.lock audits, locked NuGet restores, and SourceLink embedded debug metadata10. By synthesizing these constraints into a verifiable state machine, the control plane ensures that every released artifact is accompanied by an unbroken chain of cryptographic custody.

## **2\. Campaign Phase and State Diagram**

The campaign state machine is orchestrated as a rigorously defined sequence of phases, where transitions are unilaterally dictated by the presence and mathematical validity of output receipts. The system recognizes distinct transition vectors: allowed transitions (proceeding to the next phase upon receipt verification), retry transitions (re-executing a phase following a transient environmental failure, preserving the error receipt), terminal rejection (halting progression due to irrecoverable physical or structural violations), external blockage (suspending execution while awaiting an asynchronous external event), and completion (reached exclusively when the terminal phase yields a valid receipt).
The campaign executes the following sequence of phases:
**Source Discovery and Acquisition:** The process initiates by identifying candidate model weights and associated metadata from upstream repositories. Upon discovery, the engine fetches the raw artifacts to a local staging volume. This phase yields an Acquisition Receipt, binding the remote Uniform Resource Identifier, the downloaded byte count, and the complete SHA-256 hash of the payload.
**Review and Conversion:** The raw artifact undergoes strict structural and licensing validation. If the model utilizes unsupported architectures—such as grouped-query or multi-query attention, which the current scalar TinyRustLM runtime explicitly rejects13—the orchestrator forces a terminal rejection. Valid models are subsequently transformed into the custom .slm v1 container format. This process validates the exact 108-byte binary header, enforces the FNV-1a tensor naming contract, aligns tensor payloads, and computes the internal non-cryptographic checksum13. The Conversion Receipt mathematically binds the input hash, the conversion tool version, and the resulting .slm file hash.
**Native Evaluation and Model Qualification:** The system executes a deterministic evaluation on the local host to verify parser admission, scratch memory allocation, key-value (KV) cache initialization, and forward pass execution. Utilizing the predefined memory formulas—such as allocating precisely 4 × (10H \+ 3F \+ C) bytes for forward scratch1—the phase ensures the model does not trigger out-of-memory panics. Successful evaluation generates an Evaluation Receipt, qualifying the model for promotion into the candidate pool.
**Browser Rounds:** The WebAssembly (WASM) payload is instantiated within an automated, accountless browser environment. A handwritten JavaScript shell fetches the 114 KiB compiled .wasm module, allocates the memory buffer, and executes the C-style Application Binary Interface (ABI)13. The phase captures the end-to-end token generation process, yielding a Browser Receipt that proves the deterministic behavior of the artifact inside a standard browser engine.
**MemoryEndpoints Continuity:** The control plane negotiates with the live MATM (Multi-Agent Memory) endpoint. This phase proves that the system can acquire bounded local path claims from an exact base hash, transmit the appropriate Idempotency-Key headers, and accurately interpret conflict-safe 409 idempotency\_conflict HTTP responses without corrupting the local state2. The resulting Memory Receipt proves synchronous integration with the long-term memory boundary.
**P2P Preparation and Two-Lane Serving:** The fully qualified models are prepared for decentralized distribution. The orchestrator generates standard .torrent metadata files alongside IPFS Content Identifiers (CIDs)3. The artifacts are immediately hosted on local seeding daemons—one interacting with the BitTorrent protocol stack and the other operating a rust-libp2p node utilizing Yamux multiplexing and Noise encryption5.
**External Proof and Catalog Announcement:** The campaign suspends in an external blockage state until cryptographic verification is received confirming that an unaffiliated, external observer has successfully downloaded the complete artifact via both P2P lanes. Once the external Peer Receipts are collected, the system constructs a model profile and announces the verified artifact to the public registry API.
**Deployment Verification and Final Memory:** The final operations involve verifying the public availability of the catalog announcement via an unauthenticated HTTPS readback and validating package resolution via the designated dependency managers. The campaign culminates in the generation of a terminal .uai artifact and an immutable SLSA Level 3 Verification Summary Attestation (VSA), providing a permanent, cryptographic summary of the entire endeavor9.

## **3\. Receipt Graph and Versioned Schema Family**

To eliminate redundant computational overhead and establish a mathematically sound chain of custody, the control plane employs content-addressed phase identities. The fundamental principle is that execution evidence must be intrinsically bound to its specific inputs, execution environment, and toolset. The orchestrator never checks a mutable database record to determine if a phase has completed; it attempts to resolve a cryptographic hash in the durable filesystem.
Every receipt in the system is identified by a SHA-256 hash computed over a strictly defined schema: the combination of the Phase ID, the hashes of all input receipts, the specific version strings of the tools utilized, the execution timestamp, and the deterministic output payload.
For instance, an Evaluation Receipt incorporates the hash of the preceding Conversion Receipt, the semantic version and git commit hash of the tinyrustlm-runtime evaluator tool, and the diagnostic JSON output generated during the run. Similarly, a Memory Receipt binds the precise Idempotency-Key utilized in the HTTP POST request, the .uai local hash head, and the server's persisted=true response payload2. A Release Receipt binds the SLSA VSA, the exact hashes of the packages.lock.json file, and the cryptographic signatures attached to the .snupkg files9.
This design introduces a highly efficient invalidation and resumption mechanic. If an engineer commits a patch to the evaluator tool—perhaps resolving a boundary error during UTF-8 sampling18—the version string of the evaluator tool changes. When the orchestrator calculates the required Evaluation Receipt hash for the new run, the resulting target hash differs from the one currently stored on disk. The orchestrator immediately recognizes that the evaluation phase is incomplete and executes the new run. However, the calculation for the required Conversion Receipt remains unchanged, because neither the source model URL nor the conversion tool version was modified. The DAG simply reconnects the new Evaluation Receipt to the existing Conversion Receipt, entirely bypassing the need to re-download or re-convert a valid 3 GB artifact. Obsolete receipts generated by the previous tool version are never overwritten; they remain in the archive as historical evidence, while the active graph simply routes around them to the updated nodes.

## **4\. Atomic Persistence and Resume Algorithm**

The campaign state machine must be capable of surviving abrupt process terminations—ranging from out-of-memory operating system interventions to physical power failures—without corrupting the integrity of the receipt graph. Durable filesystem operations must be rigorously enforced to prevent partial writes from being misinterpreted as valid evidence.
All receipts and metadata records are structured as bounded JSON payloads. To guarantee atomicity across various filesystems, the persistence sequence adheres to a strict multi-step protocol. First, the JSON payload is serialized into a temporary file (e.g., receipt\_a7b9...3f.json.tmp) located within the exact same directory as the intended final destination. This guarantees that the temporary file and the final file reside on the same filesystem mount, preventing the operating system from falling back to a non-atomic copy-and-delete operation. Second, the system executes an fsync() system call on the temporary file's descriptor, forcing the underlying operating system to flush its write buffers to physical media. Third, an atomic rename operation is invoked. On POSIX-compliant systems, the standard rename() call guarantees atomic replacement. However, on Windows environments, the implementation must explicitly invoke the ReplaceFileW API to ensure strict atomic substitution semantics without introducing a microscopic window where the file appears absent. Finally, an fsync() is executed on the directory's file descriptor to ensure the directory entry modifications are durable.
The system incorporates explicit safeguards against resource exhaustion. The JSON schema enforces strict bounds on the size of embedded log outputs and trace strings. If an execution trace exceeds the maximum byte allowance, the payload is deterministically truncated or paginated. Furthermore, if the physical disk approaches maximum capacity, the write operation to the temporary file will fail prior to the atomic rename. The orchestrator catches the ENOSPC standard error, safely discards the temporary file, transitions the affected artifact's state to a graceful Blocked(DiskFull) status, and suspends the queue without corrupting the existing receipt graph.
Processing large model assets introduces a specific memory risk. Host transfers involving .slm artifacts that reach the 128 MiB boundary1, or raw parameter files approaching several gigabytes, cannot be contiguously loaded into active memory. During the generation of Acquisition and Conversion Receipts, the orchestrator opens the target files utilizing sequential scan flags and reads the data in fixed 4 MiB chunks. These chunks are streamed sequentially through a rolling SHA-256 context, ensuring that the maximum resident memory footprint remains stable regardless of the artifact size.
Upon initialization or recovery, the orchestrator executes a validation pass over the history archives. For every receipt discovered on disk, the system recalculates the SHA-256 hash of its serialized contents. If the computed content hash diverges from the hash embedded in the filename, the receipt is immediately quarantined as corrupted evidence. Only receipts that pass this mathematical proof are admitted into the active in-memory DAG, ensuring the system resumes from a state of absolute cryptographic certainty.

## **5\. Privacy and Redaction Contract**

The campaign must generate exhaustively detailed evidence to satisfy SLSA Level 3 provenance requirements and public capability claims9. However, this transparency must never compromise security perimeters, organizational tenancy boundaries, or intellectual property. The control plane enforces a strict redaction contract that dictates the exact boundaries of evidence minimization.
Receipts are explicitly authorized to store non-sensitive cryptographic material and operational telemetry. This includes public identifiers, the SHA-256 hashes of inputs and outputs, byte sizes (e.g., documenting the exact 17,160,000 byte footprint of the TinyLM-16M q8 artifact13), version strings, parallel execution counts, node latencies, and public-safe .uai summaries2. Furthermore, bounded error codes and stable diagnostic messages—such as 409 idempotency\_conflict during a concurrency collision—are safely recorded2.
Conversely, the schema categorically forbids the inclusion of sensitive operational data. Receipts must systematically exclude raw generative prompts, proprietary system prompt templates, and raw hosted-memory payloads. Cryptographic secrets, including raw credentials, Bearer tokens, MemoryEndpoints workspace keys, and PKCE authorization codes, are strictly prohibited from serialization2. Additionally, private absolute file paths that could inadvertently expose underlying operating system usernames, continuous integration server directory structures, or credential-bearing invitation URLs are masked.
To guarantee compliance with these rules, a mandatory redaction interceptor processes every payload immediately prior to JSON serialization. This engine utilizes high-entropy regex pattern matching and Shannon entropy analysis to detect strings resembling base64-encoded tokens, private keys, or API credentials. Any matched string is irrevocably replaced with a standardized \<REDACTED\_SECRET\> token. The integrity of this redaction pipeline is continuously verified by a suite of automated tests that inject known dummy credentials into simulated execution environments; if the output payload contains any trace of the dummy secret, the pipeline triggers a fatal assertion, preventing the release of the artifact.

## **6\. Blocker Taxonomy with Parallel Work Paths**

Campaign progression is rarely linear. When an operation encounters a failure condition, the control plane does not trigger a global halt. Instead, the orchestrator classifies the blocker according to a rigorous taxonomy, isolating the failure to the specific DAG branch and allowing orthogonal work to proceed uninterrupted.

| Blocker Category | Description | Parallel Work Permitted |
| :---- | :---- | :---- |
| **Insufficient Model Quality** | The generative output of a specific model consistently fails heuristic evaluation (e.g., looping, catastrophic hallucination). | Sibling candidate models continue their evaluation phases. Infrastructure tests, such as C ABI memory bounds verification, remain active. |
| **Unsupported Architecture** | The model relies on architectural patterns explicitly rejected by the parser (e.g., Multi-Query Attention in the current TinyRustLM build13). | The specific artifact transitions to terminal rejection. All other structurally valid models continue the pipeline. |
| **Acquisition Drift** | The upstream repository alters a model weight file in place without bumping a semantic version tag, resulting in a hash mismatch. | The artifact is quarantined. Supply-chain security scans (e.g., cargo-audit19) and evaluation of unaffected models proceed. |
| **License Ambiguity** | The artifact's license cannot be programmatically verified against the approved cargo-deny allowlist (e.g., MIT/Apache-2.0)12. | The artifact suspends in an external blockage state awaiting legal review. Independent P2P preparations for verified models continue. |
| **Evaluator Defect** | A bug within the WebAssembly runtime or the Rust evaluator triggers an out-of-bounds memory panic or infinite loop. | The evaluation branch pauses. However, external proof gathering, catalog announcements, and P2P lane seeding of previously qualified models remain active. |
| **Missing Live Enrollment Contract** | The system fails to authenticate with the MemoryEndpoints API due to a missing or invalid workspace bearer key or unapproved PKCE claim2. | Offline Native Evaluation, Conversion processes, and local BitTorrent/libp2p seeding continue undisturbed. |
| **Company Cleanup Failure** | The automated cleanup routine fails to verify the erasure of active .uai test memory on the remote MATM server. | Human intervention is requested. Browser rounds targeting local transient memory continue execution. |
| **Absent External Observer** | The system cannot locate unaffiliated DHT peers on the BitTorrent or libp2p networks to satisfy the external download proof3. | Browser evaluation rounds and MemoryEndpoints continuity operations proceed while the network listener idles. |
| **Signing Credential Absence** | The environment is missing the necessary X.509 certificates or NuGet API keys required to generate .snupkg files or the SLSA VSA9. | All preceding phases—including evaluation, browser rounds, and local P2P preparation—continue up to the deployment gate. |

## **7\. Test and Release Gate Matrix by Component and RID**

The evidence model must guarantee that all delivered components function deterministically across their intended target platforms, formally identified by their Runtime Identifiers (RIDs). The control plane enforces a strict semantic boundary distinguishing successful cross-compilation, software emulation, and physical hardware execution. Mocks and network loopbacks are expressly forbidden from satisfying live test requirements.

| Component | Target RID | Required Evidence Level | Acceptance Gate Description |
| :---- | :---- | :---- | :---- |
| **Rust Runtime** | linux-x64 | Real Hardware Execution | Binary header inspection validates the ELF structure. cargo test suite execution and deterministic loading of the .slm container must occur on a physical or virtualized x64 runner, producing verified JSON diagnostics. |
| **Rust Runtime** | win-x64 | Real Hardware Execution | Native MSVC build success and Portable Executable (PE) header validation. Runtime smoke tests must successfully parse and execute the forward pass on a physical Windows host. |
| **Rust Runtime** | linux-arm64 | Real Hardware Execution | Emulated execution via QEMU is explicitly rejected as it often obscures architecture-specific memory alignment faults. The test matrix must execute directly on physical ARM64 silicon (e.g., AWS Graviton instances), yielding a verifiable diagnostic payload. |
| **WASM Assets** | wasm32-unknown-unknown | Real Browser Execution | A headless browser runner (utilizing V8 or SpiderMonkey) must fetch the static 114 KiB compiled WebAssembly module, instantiate it without external imports, and invoke the raw C-style ABI for allocation and generation13. |
| **C ABI** | Cross-Platform | Fuzzing & Memory Bounds | Automated fuzzing continuously probes the WASM/C boundary, strictly verifying that raw allocation requests exceeding the 128 MiB ceiling are rejected gracefully. Includes validation of UTF-8 strings and null pointer handlers1. |
| **C\# Wrappers** | any | Integration Tests | Interoperability checks validating the safe marshaling of memory between managed .NET arrays and the unmanaged WASM boundaries, ensuring garbage collection does not prematurely free active tensor buffers. |
| **NuGet Packages** | .nupkg & .snupkg | Package-Consumer Validation | Isolated consumer test projects execute dotnet restore \--locked-mode to verify dependency resolution20. Validation includes utilizing SourceLink metadata embedded within the PDBs to dynamically fetch source files11. |
| **MiniModel Metadata** | any | Checksum & Integrity | The parser strictly validates the custom 108-byte header offset, confirms the presence of the SLM1 magic bytes, and enforces the tensor directory shape contracts, dtype alignments (f32, q8\_0, q4\_0), and checksum limits13. |

## **8\. Supply-Chain and Publication Controls**

To guarantee the integrity of the release artifacts and protect consumers from upstream compromises, the campaign integrates exhaustive Supply-chain Levels for Software Artifacts (SLSA) Level 3 controls8. These mechanisms provide verifiable, tamper-evident records detailing the precise origins and compilation paths of the software.
For the Rust and C++ components, dependency resolution is strictly controlled. The Cargo.lock file is committed to version control and mandated during all build processes, pinning the exact versions and SHA-256 checksums of every transitive crate12. Prior to compilation, the system invokes cargo-audit to cross-reference the locked dependencies against the RustSec advisory database; any identified vulnerabilities (e.g., RUSTSEC-2022-0051) immediately halt the build pipeline19. Simultaneously, cargo-deny enforces organizational policy, ensuring all dependencies comply with the approved license allowlist (e.g., MIT, Apache-2.0) and preventing the introduction of banned or duplicated crates12. To provide lasting transparency, the cargo-auditable utility embeds the complete dependency graph directly into the compiled native executable, allowing downstream container scanners to accurately catalog dependencies even after the source tree has been stripped22.
The .NET and NuGet deployment tiers operate under equally stringent rules. Continuous integration servers are configured with the MSBuild properties \<RestorePackagesWithLockFile\>true\</RestorePackagesWithLockFile\> and \<RestoreLockedMode\>true\</RestoreLockedMode\>. This forces the NuGet client to rely entirely on the packages.lock.json file during restoration; if a floating version or a transitive dependency drifts, the restore fails securely rather than silently adopting the unverified code10.
Debugging and source code traceability are managed via Symbol Packages. The build system is configured to emit .snupkg files alongside the primary .nupkg library files. The .snupkg files exclusively contain portable Program Database (PDB) files17. Through the integration of SourceLink, these PDBs are embedded with repository URLs and exact git commit hashes, allowing a consumer's Visual Studio debugger to seamlessly download the precise, immutable source files corresponding to the executed binary on demand11.
The publication phase is governed by strict authorization and provenance generation. The orchestrator invokes cargo-cyclonedx to generate a comprehensive Software Bill of Materials (SBOM), standardizing the components via Package URLs (purl) and Software Identification (SWID) tags12. Finally, an SLSA Verification Summary Attestation (VSA) is generated and cryptographically signed, attesting to the builder's identity, the isolated build environment, and the exact sequence of commands executed9. The artifact and its accompanying evidence traverse a malware-scanning boundary before the automated system is permitted to execute the authorized push to the public NuGet index and external endpoints.

## **9\. Progress Dashboard Specification**

Operational visibility into the campaign is provided by a concise, real-time dashboard that derives its metrics exclusively from the cryptographic receipt DAG. Because the dashboard queries the durable filesystem for verified receipts rather than relying on ephemeral test suite outputs, it is mathematically impossible for the dashboard to claim a task is complete based merely on a unit test or mocked interaction.
The dashboard surfaces the following Key Performance Indicators (KPIs):

* **Qualified Models:** Displayed as \[ X / 20 \]. This counter increments only when the system locates a valid Qualification Receipt for a distinct model hash, proving successful native parser admission and forward pass execution.
* **Clean Browser Rounds:** Displayed as \[ X / 50 \]. Requires the presence of 50 unique Browser Receipts, each demonstrating full token generation and deterministic memory release within the isolated WebAssembly sandbox.
* **Live Memory Rounds:** Displayed as \[ X / 25 \]. Validated by counting Memory Receipts that contain the cryptographic binding of the Idempotency-Key and the remote server's persisted=true UAIX payload confirmation2.
* **Externally Proven Lanes:** Displayed as \[ X / 40 \]. Representing 20 models distributed across 2 separate networks (BitTorrent and libp2p). This counter requires Proof Receipts documenting verifiable external IP interactions, latency metrics, and completed transfer hashes3.
* **Announced Models:** Displayed as \[ X / 20 \]. Verified by Catalog Announcement Receipts containing HTTP 200 OK responses from the registry endpoint.

In addition to the core KPIs, the dashboard provides critical operational telemetry. The **Current Operation** feed displays the specific active thread (e.g., Streaming SHA-256 hash validation for candidate \#14). The **Elapsed Time** tracks the total wall-clock duration since campaign initialization. The **Resumable State** metric provides a boolean health check, confirming that the continuous background checksum validation of the receipt archive has detected no corruption. Finally, the **Active Blockers** pane aggregates all suspended nodes currently occupying a terminal or externally blocked state, providing engineers with immediate, actionable context regarding stalled branches.

## **10\. Failure-to-Regression Workflow**

The campaign architecture treats failure not as an anomaly, but as the primary catalyst for system resilience. When raw "dogfood" operations expose a defect—such as an out-of-bounds memory read in the C ABI, a catastrophic restart leak in the browser shell, or an unexpected P2P Multiaddr routing drift6—the control plane mandates a rigorous failure-driven improvement loop.
First, the orchestrator must preserve the failure. The system takes an immediate snapshot of the execution state, generating a durable Error Receipt. This receipt cryptographically binds the specific .slm hash being processed, the precise error code, the execution stack trace, and a bounded snapshot of the active memory state prior to the crash1.
Second, the failure is transformed into a general regression test. The memory payload is passed through the redaction engine to strip any active proprietary prompts or internal paths, and the sanitized payload is committed as a deterministic test fixture within the project's primary testing repository.
Third, engineering develops a scoped fix. Once the defect—such as a buffer overrun in the scalar CPU logic or an unhandled JSON parsing exception—is resolved, the semantic version or commit hash of the tinyrustlm-runtime tool is incremented.
Fourth, the control plane initiates the rerun process. Because the tool version is a fundamental component of the SHA-256 ID in the receipt schema, upgrading the tool mathematically invalidates the specific downstream receipts that utilized the broken version (e.g., Native Evaluation, Browser Rounds). However, the preceding Acquisition and Conversion receipts retain their integrity. The orchestrator seamlessly resumes the campaign, bypassing the 3 GB download and conversion steps, and executes only the invalidated phases using the corrected toolchain.
Finally, upon successful execution, the newly generated receipts are integrated into the DAG, and a post-mortem .uai memory summary detailing the defect, the regression test, and the resolution is synchronized with the MultiAgentMemory durable endpoint for long-term project knowledge retention25.

## **11\. Final Acceptance Checklist with Objective Evidence**

The campaign state machine is prohibited from entering the Completion state until the DAG definitively proves the existence of the following objective evidence bounds. Partial success or simulated metrics cannot satisfy these requirements.

* \[ \] **20 Distinct Qualifying Hashes:** The receipt archive contains exactly 20 successful Native Evaluation receipts. Each receipt must demonstrate successful execution on real hardware (x64 and physical ARM64) and must correspond to a unique, verified .slm hash.
* \[ \] **50 Passing Deletion-Backed Browser Receipts:** Cryptographic evidence confirming 50 separate WASM instantiations, end-to-end decodes, and subsequent memory free operations within a headless browser environment, with zero evidence of memory leaks13.
* \[ \] **25 Live Company Cleanup and Restore Receipts:** Proof of interaction with the live MemoryEndpoints API, utilizing valid Idempotency-Key headers, resolving 409 concurrency conflicts gracefully, and successfully reading back public-safe .uai summaries2.
* \[ \] **40 Current Outside-Proof Receipts:** Network logs and cryptographic signatures confirming that the 20 distinct models were successfully fetched by unaffiliated, external peers. This proof must explicitly cover both the BitTorrent (Mainline DHT) protocol and the libp2p/IPFS multiaddr routing infrastructure3.
* \[ \] **20 Live Catalog Announcements:** Verified HTTP 200 OK responses from the registry API, embedded within Catalog Announcement Receipts.
* \[ \] **Package Verification:** Cryptographic proof of a successful dotnet restore \--locked-mode execution against the published .nupkg artifacts, and verification that the accompanying .snupkg is correctly resolved via symbols.nuget.org17.
* \[ \] **Public HTTPS Readback:** Successful HTTP GET verification of the public-facing documentation and metadata profiles.
* \[ \] **No Secret Exposure:** A verifiable pass signature from the redaction test suite, executed across the entire generated receipt archive prior to publication.
* \[ \] **Explicit Remaining Risk Section:** A final, automatically generated .uai document appended to the release notes detailing the known limitations of the current architecture, such as the reliance on a non-cryptographic internal checksum within the SLM1 container specification13.

## **12\. Prioritized Implementation Plan**

The realization of this control plane requires a sequenced, phased implementation approach to ensure systemic stability at each layer of abstraction.

1. **Phase I: Data Architecture and Persistence.** Develop the core content-addressed receipt DAG. Implement the atomic JSON writing primitives (including strict adherence to POSIX rename and Windows ReplaceFileW semantics) and deploy the regex/Shannon entropy secret-redaction suite.
2. **Phase II: Native and Browser Automation.** Integrate the tinyrustlm-runtime test fixtures, connect the V8/SpiderMonkey headless browser runners for WASM validation, and implement the continuous fuzzing routines targeting the 128 MiB C ABI memory boundaries1.
3. **Phase III: Live API Integration.** Construct the MemoryEndpoints connectivity layer, ensuring strict compliance with PKCE authorization flows, idempotency key requirements, and local .uai hash head management2.
4. **Phase IV: P2P Network Seeding.** Deploy the dual-lane distribution architecture. Instantiate the BitTorrent tracker/seeder clients and configure the rust-libp2p daemons, establishing the necessary Yamux multiplexing and Noise cryptographic channels5.
5. **Phase V: Supply Chain Enforcement.** Embed the SLSA Level 3 controls into the CI/CD pipeline. Enforce cargo-audit, cargo-deny, and cargo-auditable for the Rust ecosystem, alongside stringent NuGet lock file configurations and SourceLink metadata generation9.
6. **Phase VI: Control Plane Orchestration.** Finalize the state machine transition logic, deploy the real-time operator dashboard, and validate the failure-regression loop using injected faults.

## **13\. Unknowns Requiring Local or Authorized Production Access**

While the control plane relies heavily on deterministic local execution, specific parameters and validation phases cannot be accurately simulated and strictly require authorized access to the production environment:

* **Real Hardware Execution on ARM64:** Emulation engines, such as QEMU, frequently mask architecture-specific memory alignment faults and pointer arithmetic anomalies. Validating the C ABI and runtime execution requires authorized provisioning of physical ARM64 servers (e.g., AWS Graviton infrastructure).
* **Live MemoryEndpoints Credentials:** Validation of the continuity phase requires authorized, live connector pairings, API keys, and workspace bearer tokens to interact with the production MATM environment.
* **X.509 Signing Certificates:** Finalizing the release and generating the SLSA VSA requires access to authorized organizational cryptographic certificates and NuGet API keys, which are tightly controlled via secure keystores9.
* **External Network Topologies:** Generating genuine P2P Proof Receipts requires live, uncontrolled network conditions. Evaluating true Network Address Translation (NAT) traversal (e.g., STUN/TURN, hole punching) and monitoring DHT propagation latencies across global internet topography cannot be replicated via local mock probes27.
