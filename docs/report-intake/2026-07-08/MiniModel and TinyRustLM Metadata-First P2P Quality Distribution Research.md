# MiniModel and TinyRustLM Metadata-First P2P Quality Distribution Research

## Public baseline and design boundary

MiniModel.org’s current public boundary is already unusually close to the right architecture for metadata-first P2P: it describes itself as a source catalog for checksum-bound tiny model packages that users obtain, verify, transfer by consent, and run locally, while explicitly stating that it is **not** a model-hosting or inference service. The public site also says there should be no server-side execution, no hosted runnable model weights from MiniModel.org, and that every package is identified by checksums and provenance. Its roadmap calls for a `.slm` manifest, a verifier, static catalog metadata with signed index snapshots, share metadata, an optional peer companion, and browser handoff only after local verification. TinyRustLM’s public UI matches that boundary: it emphasizes local `.slm` import, says files stay on-device and are checked before they run, exposes metadata loading and receipt-ledger tooling, and frames P2P import around peer proof, manifests, and a consenting known-peer URL rather than opaque remote download flows. citeturn2view1turn12view0turn12view3turn3view2turn3view3turn3view4turn3view7

That baseline is strong because it aligns with proven patterns from software supply-chain and decentralized distribution systems. TUF is specifically designed to secure update metadata against repository compromise, rollback, and freeze-style failures through signed metadata, delegations, expiry, and consistent snapshots. Sigstore and Cosign provide practical signing and verification for blobs and bundles. DSSE exists to sign arbitrary data safely without JSON canonicalization pitfalls, and Sigstore bundles can carry DSSE-wrapped in-toto statements. in-toto and SLSA add a standard way to express verifiable provenance claims about how an artifact was produced. For discovery and peer presence, libp2p pubsub, rendezvous, and Kad-DHT show how to separate “who has something” from “the bytes themselves,” while IPNI demonstrates large-scale indexing of content-addressable data without turning the index into the data host. BitTorrent v2’s Merkle-root design shows a mature way to verify file pieces before full assembly. citeturn10view0turn10view1turn16view0turn16view1turn10view2turn16view2turn10view4turn16view3turn16view4turn10view5turn10view6

The implication is that MiniModel.org and TinyRustLM should double down on a strict separation of concerns. The **catalog** should publish signed metadata only. The **peer layer** should publish presence and piece-availability only. The **user’s device** should be the trust decision point for revalidation, import, and execution. The only exception to “no project-hosted model bytes” should be explicitly labeled public demos, kept outside the default catalog path and marked so clearly that users never confuse demo hosting with the production distribution model. That recommendation follows both the current explicit no-hosting boundary and TinyRustLM’s existing public demo language. citeturn2view1turn12view0turn12view3

## Recommended public catalog schema

The current public catalog already includes many of the right primitives: `model_id`, `display_name`, `publisher_id`, `manifest_route`, `license_route`, `artifact_kind`, `artifact_byte_count`, `artifact_sha256`, `peer_offer_route`, Merkle/chunk fields, `source_kind`, `source_identity`, `slm_quantization`, multiple `.slm` checksums, `quality_claim`, `trained_quality_claim`, and `evidence_admission_status`. It also publishes top-level statements that the project server does not serve or run model bytes, and it references a separate peer-source announcement catalog by hash. That is an excellent starting point; what is missing is a crisper public distinction between **identity**, **compatibility**, **quality evidence**, **trust status**, and **abuse posture**. citeturn3view2turn3view5turn2view1

The recommended public catalog fields should look like this:

| Field group | Recommended public fields |
|---|---|
| Identity | `model_id`, `display_name`, `publisher_id`, `publisher_key_id`, `manifest_uri`, `manifest_sha256`, `manifest_signature_uri`, `catalog_snapshot_id`, `catalog_snapshot_version` |
| Boundary | `project_server_serves_model_bytes`, `project_server_runs_model_bytes`, `project_server_proxies_model_bytes`, `demo_only`, `artifact_project_server_url` |
| Artifact identity | `artifact_kind`, `artifact_file_name`, `artifact_byte_count`, `artifact_sha256`, `chunk_algorithm`, `chunk_size`, `chunk_count`, `chunk_list_sha256`, `merkle_root_sha256` |
| `.slm` compatibility | `slm_quantization`, `slm_model_shape`, `slm_checksum`, `slm_tokenizer_checksum`, `slm_tensor_layout_checksum`, `slm_config_checksum`, `min_tinyrustlm_version`, `runtime_family`, `max_context_tokens` |
| Source provenance | `source_kind`, `source_identity`, `source_revision`, `source_commit_or_revision`, `license_uri`, `source_model_card_uri`, `source_dataset_refs` |
| Quality summary | `quality_summary`, `quality_claim_class`, `quality_badges`, `eval_refs`, `local_smoke_status`, `compatibility_status`, `last_revalidated_at` |
| Eval references | `benchmark_id`, `task_id`, `metric`, `score`, `split`, `prompt_template_id`, `eval_tool`, `eval_report_uri`, `eval_report_sha256`, `eval_attestation_uri`, `issuer_id`, `community_provided` |
| Trust and policy | `evidence_admission_status`, `publisher_claims_status`, `verification_status`, `revocation_status`, `takedown_status`, `known_issues_uri`, `safety_notes_uri` |
| Peer availability | `peer_hint_status`, `peer_import_status`, `peer_source_count`, `announcement_snapshot_uri`, `announcement_snapshot_sha256`, `availability_last_seen_at` |
| UX filters | `size_class`, `language_tags`, `task_tags`, `license_tags`, `needs_local_revalidation`, `demo_available`, `warning_flags` |

This schema is intentionally conservative. It keeps the catalog metadata-only, but makes it much easier for users to answer the three questions that actually matter at discovery time: **What is this? Can I run it? Why should I trust the quality claim?** That approach is consistent with Hugging Face’s model-card guidance, which treats metadata as essential for discoverability and expects cards to describe intended uses, limitations, datasets, and evaluation results. It also matches Hugging Face’s decentralized eval model, where structured evaluation results are stored separately and linked to both the model page and the benchmark leaderboard. citeturn10view7turn10view8turn11view0

Two field-level rules matter most.

First, quality must never be a naked string. The current `quality_claim` field is a useful placeholder, but public catalogs should normalize claim classes into something like `runtime_smoke_only`, `publisher_reported_eval`, `third_party_verified_eval`, `locally_revalidated`, `deprecated`, or `disputed`. That prevents a vague “good model” label from appearing equivalent to a signed, benchmark-linked report. MiniModel’s own fixture catalog already hints at this discipline by distinguishing `quality_claim`, `trained_quality_claim`, `evidence_admission_status`, and the “next gate” required before trusting peer import. citeturn3view2turn3view5

Second, every mutable metadata document should have a stable content hash and freshness control. MiniModel already publishes peer announcement routes with a SHA-256 and calls for signed index snapshots; TUF’s model shows why that matters, because freshness and expiration are what keep an attacker from replaying stale but valid metadata indefinitely. citeturn3view2turn2view1turn10view0

## Trust and evaluation badge system

The badge system should communicate **what was verified, by whom, and at what level**. It should not imply that all validation is equal. The best model here is a layered badge stack: model-card style transparency for human readers, Hugging Face–style structured eval references for benchmark evidence, and supply-chain style attestations for signatures and provenance. Model cards were proposed precisely to disclose intended uses, evaluation procedures, and performance characteristics, including subgroup performance where relevant. Hugging Face’s model pages and `.eval_results/` mechanism already separate model documentation from benchmark-linked structured results, and they explicitly allow results to be marked “community-provided.” That distinction is exactly the one MiniModel/TinyRustLM should preserve in public badges. citeturn11view1turn11view2turn10view7turn10view8

A practical public badge set would be:

| Badge | Meaning | Requirements to display |
|---|---|---|
| **Signed Manifest** | Artifact identity is bound to a signed manifest | Valid DSSE/Cosign signature, trusted key, manifest hash matches catalog |
| **Catalog Verified** | Entry appears in a signed, current catalog snapshot | Snapshot signature valid, not expired, not revoked |
| **Runtime Smoke Passed** | The model loaded and passed basic deterministic local tests | Local verifier receipt attached; no quality implication beyond “runs” |
| **Eval Referenced** | Public eval report exists | At least one immutable eval report hash and benchmark reference |
| **Publisher Reported Eval** | Scores exist but were supplied by the publisher or source repo | Eval reference present; no trusted third-party attestation |
| **Third-Party Verified Eval** | Independent evaluator signed or countersigned the eval result | Eval attestation signed by trusted evaluator key |
| **Local Revalidated** | This specific device reran checks after import | Local receipt exists for exact artifact hash |
| **Peer Ready** | Metadata and piece proofs are sufficient for peer fetch | Valid peer offer, chunk list hash, Merkle root, and import recipe |
| **Announcement Fresh** | A recent peer presence announcement exists | Announcement signature valid and TTL not exceeded |
| **Demo Only** | Publicly hosted demo artifact; not the normal distribution path | Explicit demo flag, separate UX treatment |

The crucial UI rule is that badge colors and ordering should reflect trust hierarchy. For example, **Runtime Smoke Passed** should never sit visually above **Third-Party Verified Eval**, because “it runs” and “it performs well on task X” are different claims. Likewise, **Publisher Reported Eval** should be visually distinct from independent verification, much like Hugging Face’s “community-provided” distinction warns users that not every leaderboard entry has the same trust status. citeturn10view8turn3view2

For signatures, MiniModel should move toward a two-part public trust story. The first part is artifact identity: sign the manifest or a payload-hash envelope that binds artifact hash, chunk structure, tokenizer/config/layout checksums, source identity, and license route. The second part is evidence identity: sign eval attestations and share-kit attestations separately, ideally as DSSE-wrapped in-toto statements so the payload type is authenticated and downstream tools can reason about specific predicate types. Sigstore bundles can package those statements and their verification material, while in-toto provides the extensibility needed for custom predicates such as `minimodel.eval.v1` and `minimodel.import_receipt.v1`. citeturn2view1turn16view0turn16view1turn10view2turn16view2

The most important policy decision is this: **no green quality badge without immutable evidence**. If a model has only a source model card and no benchmark-linked report, show a documentation badge, not a quality badge. If it has a self-published eval but no independent attestation, show an amber badge. If it has a signed third-party eval or widely recognized benchmark dataset entry, show a stronger badge. That protects against fake or inflated claims while still letting early models be discoverable. It also fits MiniModel’s present habit of separating admission status from quality claim instead of collapsing them into one value. citeturn3view2turn3view5turn10view8turn11view1

## P2P import checks and local revalidation

TinyRustLM’s public UI already points to the correct trust flow: load metadata, optionally enable P2P, supply a consenting known-peer URL, import through manifests or peer proof, and keep `.slm` files local and checked before they run. MiniModel’s public examples reinforce the same sequence: the catalog references a manifest and peer offer, the share-metadata example exports chunk hashes and a Merkle root with transfer disabled by default, and the peer import request explicitly says transfer requires user consent and local re-verification before browser import. citeturn12view0turn12view1turn12view3turn3view4turn3view7

That public flow should become a formal import pipeline with four gates.

The first gate is **metadata trust**. Before any bytes move, TinyRustLM should verify the current signed catalog snapshot, its expiry, the entry’s manifest hash, the manifest signature, and any revocation or takedown pointers. TUF is the right conceptual model here because it directly addresses snapshot freshness, delegated trust, and freeze/rollback attacks. For implementation, Cosign verification of blobs or DSSE bundles would be sufficient for simple deployments, while a fuller TUF-style repository can be layered in as the catalog grows. citeturn10view0turn10view1turn16view0turn16view1

The second gate is **piece trust**. Peer import should always be piece-verified before full assembly. MiniModel is already publishing chunk lists and a Merkle root in both catalog/share metadata, and BitTorrent v2 demonstrates why this is the correct primitive: a file’s Merkle root remains stable for identical content, and piece/block verification can happen before the complete file exists. In practice, TinyRustLM should fetch pieces only after checking the declared chunk list hash and peer offer hash, then verify each piece hash and the Merkle root as assembly proceeds. A malicious peer should be able to waste time, but not trick the client into accepting altered bytes. citeturn3view2turn3view4turn10view6

The third gate is **artifact revalidation**. After assembly, recompute the full artifact SHA-256 and all `.slm` structural checksums exposed publicly: model checksum, tokenizer checksum, tensor-layout checksum, and config checksum where available. If any checksum differs, import should hard-fail and the local receipt should record the mismatch. This is especially important because public catalogs may list multiple variants of a seemingly similar model; the checksums are what prevent “same name, different bytes” confusion. MiniModel’s public catalog already exposes exactly these checksum families, which is a major advantage over ordinary model marketplaces. citeturn3view2turn3view5

The fourth gate is **local runtime quality validation**. This should be modest, deterministic, and intentionally separate from benchmark scoring. At minimum, TinyRustLM should run a local smoke suite after import: open-the-model, tokenize/de-tokenize a tiny fixture, run a fixed low-token prompt with deterministic settings, verify memory fit, verify context size, and confirm the output hash or output shape expected for the fixture class. The result should award only a “Runtime Smoke Passed” status, never a generalized quality endorsement. That distinction matches TinyRustLM’s public “checked before they run” positioning and MiniModel’s own current `runtime-execution-smoke-only` quality pattern. citeturn12view0turn3view2

Import receipts should then be first-class public-format artifacts, but locally generated. The best design is a local append-only receipt ledger where each receipt captures: artifact hash, manifest hash, catalog snapshot hash, peer offer hash, peer endpoint or peer ID, import timestamp, piece-verification result, full-hash result, checksum results, runtime smoke result, policy version, and operator decision. Those receipts should be exportable in a redacted form but private by default. in-toto is a strong fit for the receipt object because it is expressly for verifiable claims about how an artifact was produced or checked, and DSSE is a good envelope for signing the receipt if the user chooses to share it. TinyRustLM’s public interface already exposes “Import receipt ledger JSON,” which makes this recommendation a natural extension rather than a new concept. citeturn10view2turn16view0turn12view2turn12view3

## Discovery flow for users, peers, and local share kits

The discovery experience should start with metadata-only search, not byte acquisition. TinyRustLM already points users toward “Hugging Face model cards first,” lets them browse metadata, and allows loading MiniModel metadata or a local `models.v0.json` snapshot to find proof-ready peer imports. That is the right user mental model: search first, inspect evidence second, import third. citeturn12view0turn12view3

A good user-facing discovery flow would be:

1. **Search metadata only.** Results should come from the signed catalog snapshot and optionally user-supplied local catalogs, with filters for task, size, quantization, license, language, and badge state. No model bytes should move during search. citeturn3view2turn12view0

2. **Open an evidence drawer.** Each result should show a compact summary: compatibility, artifact size, trust badges, source identity, license, and whether the project itself hosts bytes. Expanding the drawer should reveal manifest information, eval references, model-card links, peer readiness, and warnings. This is the strongest place to teach users the difference between “runs,” “documented,” and “benchmark-verified.” citeturn10view7turn10view8turn3view2

3. **Choose the import lane.** The UI should clearly separate Local File, External Source, and P2P Import. TinyRustLM already exposes those lanes. P2P should remain opt-in and should require an explicit known-peer choice until a more mature peer companion exists. citeturn12view0turn12view1turn2view1

4. **Run local revalidation automatically.** After import, the user should get a concise outcome screen: “Verified identity,” “Passed runtime smoke,” “Has publisher-reported eval,” “No independent eval,” and so on. That screen should end with a local receipt entry, not a vague success notification. citeturn12view2turn3view7

Peer announcements should remain metadata-only and ephemeral. MiniModel’s public catalog already points to a separate announcement feed by SHA-256, and the current public announcement feed is empty, which is actually good discipline because it proves the system can represent “no current peer availability” without inventing false presence. As MiniModel evolves, announcements should remain separate from catalog entries and should carry TTL/freshness so the UI can distinguish live availability from stale rumor. libp2p rendezvous is especially relevant here because it supports namespace-scoped registration with signed peer records and bounded lifetimes, precisely the pattern needed for “who currently offers pieces for artifact X?” discovery without central byte hosting. Kad-DHT or IPNI-style provider lookup can come later if the system needs broader scale. citeturn3view2turn3view3turn16view3turn16view4turn10view5

Local share kits should be zero-byte metadata bundles by default. MiniModel’s current example already heads in that direction: it binds the artifact SHA-256, chunk hashes, chunk list hash, Merkle root, catalog-entry candidate, and transfer flags, with live transfer disabled. That is almost exactly what a safe share kit should be. I would formalize the exported kit as containing: the catalog-entry skeleton, manifest hash, peer-offer hash, chunk inventory proof, optional peer contact card, optional permission policy, and an optional redacted import receipt proving the sharer locally verified the same artifact. By default, it should contain **no model bytes** and **no active endpoint**. Separate “turn on sharing” and “export share kit” so that preparing metadata is not the same as authorizing transfer. citeturn3view4turn12view4turn12view1

## Anti-abuse and fake-claim controls

The main abuse risks here are not just corrupted bytes. They are stale metadata, forged evaluator identity, misleading quality claims, fake peer availability, benchmark gaming, and subtle “same model name, different artifact” impersonation. The public design should therefore treat quality claims as adversarial unless corroborated. TUF’s freshness controls are the answer to stale catalog/snapshot abuse; DSSE, Cosign, and in-toto are the answer to identity and attestation authenticity; Merkle-based piece verification is the answer to byte tampering; and model-card/eval separation is the answer to documentation theater masquerading as evidence. citeturn10view0turn10view1turn16view0turn10view2turn10view6turn10view7turn10view8

The specific anti-abuse rules should be strict.

A quality badge should only be granted if the associated evidence is immutable and hash-addressed. That means every eval reference should include a content hash, the benchmark/task/metric/split, the evaluator identity, and ideally a signed attestation. If MiniModel ingests a Hugging Face model card or eval result, it should record the exact source URI and hash of the referenced material at ingestion time. This prevents “repo owner silently edited the README later” from rewriting what the badge meant when the catalog snapshot was signed. Hugging Face’s model-card and `.eval_results/` structure already provides a practical external source lane for this kind of reference-based ingestion. citeturn10view7turn10view8

Publisher self-claims and independent verification must never share the same badge class. A self-reported “MMLU 63.1” claim should not render like an independently rerun or third-party-signed result. The UI should always show the issuer. In other words, trust is attached to the **claim issuer**, not only the claim content. That is exactly how in-toto/SLSA-style attestations are meant to be consumed: a statement is meaningful because a trusted builder or verifier made it, not because the JSON looked plausible. citeturn16view2turn10view2

Benchmark contamination and leaderboard overfitting should be acknowledged in the product, not hidden. Research on benchmark contamination shows that public benchmark scores can be inflated when evaluation data leaks into training data, and HELM’s core motivation is that model capabilities, limitations, and risks require broader, transparent evaluation across scenarios and desiderata. That means MiniModel should avoid a single all-purpose “quality score” badge. Instead, it should let users inspect scenario-specific evidence and label benchmark reports with provenance, dataset date, and contamination-risk notes when relevant. citeturn13search0turn13search4turn13search3

Peer announcements should also be treated as low-trust by default. A peer saying “I have artifact hash X” is not a quality claim and not enough to prioritize the item in discovery. Announcements should be signed, short-lived, rate-limited, and strictly separated from quality badging. libp2p rendezvous and pubsub are useful here precisely because they are about discovery and coordination, not endorsement. MiniModel’s current empty announcement feed is a healthy precedent: presence is optional and can be absent without degrading artifact identity. citeturn16view3turn10view4turn3view3

Finally, the catalog should support negative trust signals as first-class metadata. Add revocation and dispute handling with fields such as `revocation_status`, `revoked_keys`, `disputed_eval_refs`, `takedown_status`, and `warning_flags`. MiniModel already exposes a takedown contact route and has a documented no-hosting boundary; extending that to signed denylist and dispute metadata would let TinyRustLM warn users without centralizing model bytes. If a key is compromised or an evaluator is caught making false claims, clients should be able to receive signed revocation metadata and downgrade or remove the relevant badges automatically. citeturn3view2turn2view1turn10view0

Overall, the strongest public posture for MiniModel.org and TinyRustLM is: **metadata is public, bytes are local or peer-fetched by consent, quality is evidence-linked, and trust is always re-earned on the importing device**. That design fits the projects’ current public boundary, uses mature cryptographic and P2P building blocks, and gives users a practical way to find models that really work without turning the project server into a model host. citeturn2view1turn12view0turn3view2turn3view4turn3view7turn10view0turn16view0turn10view8
