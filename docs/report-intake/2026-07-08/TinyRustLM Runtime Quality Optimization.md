# **Runtime Quality Research: Transforming TinyRustLM Generation from Fixture to Coherence**

The development and deployment of locally executed, browser-based small language models (SLMs) represent a critical frontier in constrained-environment machine intelligence. TinyRustLM, a dependency-free Rust runtime compiled to WebAssembly (WASM), provides an architectural foundation for such local deployments. However, the current iteration of the system relies on "deterministic smoke" models, such as the TinyLM-16M configurations, which are untrained parameter arrays designed strictly for verifying binary interfaces, tensor materialization, and mathematical execution paths1. While these fixtures confirm the integrity of the WebAssembly Application Binary Interface (ABI) and the parser layer, they do not produce trained, conversational intelligence. Consequently, generating genuine, coherent local responses requires crossing the boundary from topological verification to rigorous, state-aware autoregressive decoding.  
When a causal language model runtime emits "fixture-like" output—characterized by endless repetition loops, hallucinated prompt injections, deterministic stalling, or a failure to halt at natural boundaries—the underlying failure modes are typically mechanical rather than purely parameter-driven. The transition to high-quality text generation necessitates comprehensive structural refinements within the runtime's memory management, its state machine, and its sampling pipelines. The analysis herein dissects the core mechanics of tokenization correctness, prompt encoding, Key-Value (KV) cache discipline, repetition control, chat template design, and state transaction boundaries within the TinyRustLM ecosystem. The objective is to outline the precise engineering interventions required to elevate the .slm load and generation paths to support coherent, production-ready inference without relying on hidden remote inference, browser-side fake output, or hardcoded prompt hacks.

## **Architectural Constraints and the Model Container Ecosystem**

To accurately diagnose runtime generation failures and propose viable Rust-native fixes, the operational parameters of the TinyRustLM architecture must be established. The system operates on a single-threaded scalar CPU execution model compiled directly to WASM, running natively within the browser's main thread2. This execution paradigm fundamentally limits immediate parallelization and enforces strict memory-management disciplines, as any buffer overflow or memory leak will inevitably crash the host browser tab.  
The entirety of the runtime state is managed by a single process-global Mutex\<Option\<Runtime\>\>3. This singular lock owns the active model weights, the KV cache, the tokenizer structures, the reusable scratch buffers for the forward pass, the logits arrays, the sampling states, and the emitted diagnostic telemetry3. Memory transfers between the JavaScript host environment and the WASM linear memory are governed by a strict 128 MiB single-allocation transfer ceiling2. This raw allocation accommodates the entirety of the .slm container bytes during the model-load transaction, copying the artifact into WASM memory before parsing begins3. Any architectural fix to the decoding pipeline must respect this memory envelope; expanding the KV cache indiscriminately or pre-allocating excessively large diagnostic buffers will rapidly trigger out-of-memory (OOM) traps in the browser application shell.  
Furthermore, TinyRustLM does not natively parse standard GGUF files; instead, it relies on a custom, tightly packed binary format designated as SLM13. The integrity of the generation pipeline is intrinsically linked to the accurate extraction and application of metadata embedded in this file. The .slm v1 container dictates the model topology and initialization parameters via a fixed 108-byte header, the parsing of which dictates all downstream memory allocations.

| Offset (Bytes) | Field Specification | Implications for Coherent Generation |
| :---- | :---- | :---- |
| 0–3 | Magic Number (SLM1) | Validates container architecture before the 128 MiB memory allocation is committed. |
| 16 | Flags (Bit 0\) | Determines whether the model utilizes tied output projection, directly impacting the final logits calculation3. |
| 20–52 | Model Dimensions | Defines Vocabulary size (![][image1]), Layers (![][image2]), Attention Heads (![][image3]), KV Heads (![][image4]), Head Dimension (![][image5]), and maximum Context Length (![][image6])3. |
| 56 | RoPE Theta | The base rotary frequency used for causal positioning. If misread, positional awareness collapses3. |
| 60 | RMS Epsilon | The normalization epsilon, critical for preventing gradient explosion and maintaining numerical stability3. |
| 64–80 | Tokenizer Offsets | Pointers to the embedded BTOK or BPE1 tokenizer dictionaries, determining vocabulary translation3. |

Following this fixed header, the parser encounters a 64-byte aligned tensor directory that dictates the shape, type, and placement of the model's weights. TinyRustLM supports standard f32 representations alongside quantized q8\_0 and q4\_0 formats3. Coherent generation requires that the Rust parser accurately map these multidimensional arrays into the constrained WASM linear memory without shape mismatches. Even a single byte-offset error in the output projection matrix or the final LayerNorm configuration will scramble the output distribution, resulting in uniform logits that the sampler can only interpret as noise.  
To support this decoding phase without exceeding browser limits, TinyRustLM derives its internal memory allocations dynamically from the dimensions explicitly declared in the SLM1 header. These pre-allocated buffers are retained for the lifespan of the loaded model, minimizing the latency of garbage collection and reallocation during the autoregressive loop.

| Allocation Target | Memory Formula (Bytes) | Architectural Function |
| :---- | :---- | :---- |
| Forward Scratch | ![][image7] | Provides reusable, transient memory for intermediate tensor operations (e.g., Q/K/V projections, SwiGLU activations) during a single forward pass2. |
| KV Cache | ![][image8] | Persists the Key and Value matrices across sequential generation steps, allowing the model to recall past context without full recalculation2. |
| Logits | ![][image9] | Stores the unnormalized probability distribution over the entire vocabulary space prior to the application of sampling logic2. |

These calculations expressly exclude the base allocator overhead, the temporary transfer allocation, and the JavaScript presentation buffers2. The strict mathematical relationship between the model dimensions and the memory footprint underscores the necessity of precise state management. If the runtime fails to discipline its pointers as generation progresses, these fixed allocations quickly become corrupted, leading directly to the phenomenon of degenerate text generation.

## **Diagnostic Analysis: Root Causes of Degenerate Repetition**

When a causal language model enters an endless cycle of repeated tokens, generating the same localized phrase in an inescapable loop, the output has succumbed to degenerate repetition. While the TinyLM-16M models are currently initialized with untrained, deterministic smoke weights that inherently possess low statistical entropy, an engineered runtime must prevent repetition loops even when handling perfectly flat logit distributions. The root causes of fixture-like output in the TinyRustLM environment stem from five specific mechanical deficiencies in the decoding phase, each corresponding to a failure in managing the constraints of the Rust state machine.  
The primary mechanical failure responsible for repetition loops is positional embedding stagnation. Autoregressive transformers lack inherent sequence awareness; the order of tokens must be mathematically injected into the continuous vector space. TinyRustLM utilizes Rotary Positional Embeddings (RoPE) to encode the relative position of tokens by applying a rotation matrix to the queries and keys. This rotation is fundamentally dependent on the absolute sequence index, utilizing the RoPE theta value defined at header offset 563. If the generation loop fails to continuously increment the active sequence index during the step-by-step decode phase, every newly generated token is embedded with the identical position identifier as the preceding token. Consequently, the causal attention mechanism perceives all generated tokens as occupying the exact same spatial location. This structural failure destroys the causal progression of the sequence, causing the attention matrix to collapse into a static state and forcing the model into an inescapable repetition loop, regardless of the underlying weight quality.  
Coupled with positional stagnation is the failure to maintain Key-Value cache indexing and commit discipline. To avoid the computationally prohibitive task of recalculating the attention scores for the entire sequence at every autoregressive step, the transformer caches the key and value vectors of past tokens. In TinyRustLM, this KV cache is pre-allocated as a single contiguous block calculated precisely from the model dimensions2. Coherent generation dictates a strict commit discipline where, during each forward pass, the key and value vectors for the newly generated token must be written to the cache at the correct memory offset corresponding to the current sequence length. If the pointer tracking the active sequence length is not explicitly advanced by the state machine, the runtime will continuously overwrite the data at the exact same index. As a result, the model's effective context window never expands. The decoder continuously predicts the next token based on a frozen, unchanging historical state, mathematically guaranteeing a repetitive output string.  
The third root cause of fixture-like generation lies in the unpenalized execution of the deterministic Pseudo-Random Number Generator (PRNG). TinyRustLM employs a fixed transient array capable of storing 1,024 sampling candidates to constrain memory usage during the sorting and selection phase2. The selection from these candidates is governed by a deterministic PRNG intended to ensure reproducible evaluation environments during smoke testing4. When evaluating untrained models or early-stage fine-tunes, the logit distribution is often highly uniform. If the deterministic PRNG utilizes a static mathematical seed and fails to mutate its internal state after each sampling event, it will yield the exact same random scalar on every single pass through the decoding loop. When this static scalar is applied to a relatively unshifting logit array, the sampler will deterministically select the exact same token index on the current step as it did on the previous step. Without explicit entropy mutation within the PRNG implementation, local text generation devolves into a static loop.  
Compounding the PRNG stagnation is the complete absence of explicit mathematical repetition penalties. Even optimally trained, high-parameter language models exhibit a profound statistical bias toward repetition if left unpenalized, as the natural probability masses of common tokens frequently dominate the distribution. Standard local inference architectures implement dynamic scaling parameters—specifically presence penalties and frequency penalties—that systematically suppress the logits of tokens that have already appeared in the active context window. There is no evidence in the current TinyRustLM snapshot that a repetition penalty is mathematically applied to the candidate storage array prior to the PRNG selection phase4. Without this penalty scaling algorithm, the runtime allows previously generated tokens to maintain their artificially high probability mass, causing the model to collapse into endless strings of common conjunctions or punctuation marks.  
Finally, the generation pipeline fails to properly recognize and act upon un-tracked End-of-Sentence (EOS) boundaries. Causal language models rely on specialized stop-tokens to signal the completion of a semantic thought or the end of a designated role's turn. In TinyRustLM, the selected tokenizer metadata manages these boundary markers3. If the sampling pipeline successfully selects the EOS token ID during generation, the runtime must immediately intercept this integer and cleanly halt the autoregressive loop. If the termination logic relies strictly on reaching the hard context capacity limit rather than actively monitoring for the EOS token, the model will continue to sample from the logits. Because the EOS token often acts as an absorbing mathematical state in trained models, subsequent logits become highly erratic. The model will either begin generating incoherent gibberish, hallucinate a new conversation from a different persona, or simply output the EOS string endlessly until the WASM memory buffer overflows.

## **Tokenization Correctness and Prompt Encoding Mechanics**

The transition from a raw user prompt string to a sequence of input tensor tokens, and the inverse translation from output tokens back to a coherent conversation transcript, is heavily dependent on the embedded BPE1 and BTOK components3. Tokenization correctness is not merely a string-matching exercise; it is a fundamental pillar of model comprehension, dictating how the semantic space is mathematically chunked and fed into the embedding layer.  
Byte-Pair Encoding (BPE) merge execution must rigorously honor the hierarchical dictionaries defined in the .slm container. The exact offsets and lengths defining this dictionary are extracted from the header during the load transaction3. During the prompt encoding phase, the Rust runtime must traverse the user's input string, iteratively identifying and merging adjacent byte pairs according to their explicit rank in the embedded dictionary. If the runtime takes computational shortcuts or misinterprets the merge hierarchy, it will map common semantic structures to fragmented or out-of-distribution token IDs. The forward pass will subsequently attempt to generate responses based on a hallucinated input space, severely degrading the output quality. Furthermore, the prefill module is responsible for managing specialized boundary markers. As explicitly documented, the selected tokenizer adds the Beginning of Sentence (BOS) and EOS tokens as required by the model architecture3.  
Decoding presents a distinct set of mechanical challenges, specifically regarding UTF-8 boundary streaming across the WebAssembly interface. Because a single multi-byte UTF-8 character (such as an emoji or non-Latin script) can be fractured across multiple BPE or byte-fallback tokens, the autoregressive decoder cannot simply cast every individual sampled token directly to a Rust String or a JavaScript DOMString. If it attempts to do so, the intermediate rendering will panic or emit Unicode replacement characters. The WASM presentation layer must instead accumulate the raw emitted token bytes into a dedicated transient buffer. It must mathematically verify complete UTF-8 validity before flushing the decoded string sequence over the ABI boundary to the browser interface. This ensures that the user experiences a fluid, coherent text stream, entirely masking the fragmented tokenization process occurring within the scalar CPU loop.  
Equally critical to prompt encoding is the architectural implementation of chat template formatting. A raw base language model is essentially a document completion engine; it predicts the statistically most likely text to follow the prompt. To transform this base behavior into an interactive conversational assistant, the input must be heavily structured. The prefill module must support the programmatic injection of specific chat templates (e.g., \<|im\_start|\>system\\nYou are a helpful assistant.\<|im\_end|\>\\n\<|im\_start|\>user\\n{prompt}\<|im\_end|\>\\n\<|im\_start|\>assistant\\n). Without these structural wrappers seamlessly applied by the runtime during the encoding phase, a trained instruction model will treat the user prompt as an unconstrained text completion task. It will likely hallucinate both the user and assistant roles, conversing with itself and producing highly erratic outputs that mimic the format of its training data rather than addressing the user's explicit query.

## **Sampling Configuration and Deterministic Control**

The actual selection of the next token from the ![][image9] logit array is the most highly tunable aspect of the local generation loop. Moving from a deterministic evaluation harness to a system capable of diverse, coherent generation requires exposing and managing several interrelated sampling parameters.  
TinyRustLM's reliance on a fixed 1,024-candidate sampling array2 is a deliberate architectural decision to cap transient memory allocation during the generation transaction. Instead of sorting the entire vocabulary (which frequently exceeds 32,000 tokens), the runtime must first filter the logit array down to this 1,024-element bound. This inherently acts as a strict top-k constraint, preventing the model from ever sampling the absolute lowest-probability "long tail" tokens. While this constraint guarantees execution within the scalar CPU's transient memory envelope, the distribution within that fixed array must still be manipulated to achieve high-quality output.  
The runtime must simulate or explicitly implement temperature scaling. Temperature alters the shape of the logit distribution before the probabilities are calculated via the softmax function. A temperature value less than 1.0 mathematically sharpens the distribution, driving the probabilities of the most likely tokens closer to 100% and suppressing the less likely candidates. This results in highly focused, deterministic text, ideal for coding tasks or factual recall. Conversely, a temperature greater than 1.0 flattens the distribution, elevating the probabilities of less common tokens and encouraging creative, diverse generation. If TinyRustLM forces a static temperature of 1.0 (or mathematically bypasses the softmax step entirely during smoke testing), the output will lack the necessary tuning controls required by different specialist modules.  
Furthermore, the deterministic PRNG must be fundamentally upgraded from a static, reproducible fixture into a mutating state machine. For true deterministic seed behavior—which is highly desirable in local SLMs for ensuring reproducibility during complex agentic reasoning tasks—the user must be able to inject an initial numerical seed via the JavaScript application shell. However, once that initial seed is utilized for the first token generation, the PRNG algorithm (such as a splitmix64 or xorshift implementation within the Rust core) must mathematically mutate its internal state4. This ensures that every subsequent token selection draws from a novel pseudo-random scalar, preventing the sampling loop from becoming stuck in a deterministic rut when navigating flat logit distributions. The capability to replay a specific generation trajectory is preserved by the initial seed injection, but the sequence itself becomes dynamically coherent.

## **Context Reset Behavior and the Multi-Turn Lifecycle**

A critical aspect of local generation is how the runtime manages memory across sequential requests. TinyRustLM explicitly delineates between a model-load transaction and a generation transaction2. The model-load transaction is an expensive, high-latency operation involving the 128 MiB memory transfer, the parsing of the SLM1 header, and the allocation of the massive KV cache and tensor directories. The generation transaction, conversely, encompasses the encoding, prefill, and autoregressive decoding of a single user interaction, clearing the generation state upon completion2.  
Coherent multi-turn conversations require the runtime to manage its context state dynamically without fully discarding the .slm weights from WASM linear memory and triggering a new load transaction. When a multi-turn user prompt is submitted, the system must first verify if the cumulative sequence length of the past conversation plus the new prompt exceeds the hard context capacity limit (![][image6]). If the capacity is sufficient, the new prompt tokens are encoded and appended directly to the existing sequence. The active sequence length pointer dictates exactly where the new prefill phase begins calculating attention, seamlessly integrating the new query with the historically cached Key-Value pairs.  
When the conversation terminates or the user requests a new topic, a hard "Reset context" command must be dispatched across the WASM ABI4. This command must trigger a highly specific memory management protocol within the Rust state machine. Crucially, it must *not* deallocate the 128 MiB memory block containing the model weights, nor must it release the massive KV cache memory allocations back to the WASM heap. Re-parsing the tensor directory and re-allocating memory over the host-to-WASM boundary would introduce unacceptable latency and risk memory fragmentation. Instead, the context reset behavior must be a logical soft-reset: the active sequence length pointer is simply zeroed out, the conversation transcript buffer is logically cleared, and the determinist PRNG seed is optionally reset4. The underlying KV cache memory remains allocated but is logically treated as empty, ready to be safely overwritten by the subsequent generation transaction.

## **Prioritized Implementation Fixes**

Transforming the TinyRustLM runtime from an evaluation harness into a capable local generator requires translating the theoretical root causes into actionable, prioritized engineering interventions. These modifications must be applied directly to the Rust/WASM codebase, prioritizing memory safety, tight pointer discipline, and mathematical accuracy over raw generation speed.  
The primary and most critical intervention is establishing strict KV Cache sizing, indexing, and commit discipline. The generation transaction loop must strictly decouple the absolute context capacity limit from the active, running sequence length. The Runtime struct must be refactored to maintain a mutable usize field, explicitly named active\_seq\_len, initialized to the length of the encoded prompt during the prefill phase. During the execution of the forward pass, the causal attention kernels must dynamically slice the pre-allocated KV cache using strict Rust reference bounds, such as \&cache\[..active\_seq\_len \* head\_dim\]. The runtime must explicitly panic or throw a bounded error code via the established recovery boundary3 if active\_seq\_len ever meets or exceeds the capacity ![][image6]. After the output projection is computed and before the sampling pipeline is invoked, the newly calculated key and value vectors for the current token must be explicitly copied into the cache precisely at the offset defined by active\_seq\_len. Furthermore, the RoPE calculation kernel must be updated to accept active\_seq\_len as the absolute position identifier ![][image10] for the current token computation, ensuring the frequency rotations progress causally. Immediately prior to the next decoding iteration, active\_seq\_len must be incremented by 1\.  
The second mandatory intervention is the implementation of mathematical repetition penalties directly into the logit pipeline. Before the raw logits are sorted and filtered into the 1,024-candidate fixed array, the runtime must iterate over the active context transcript and mathematically depress the probabilities of previously generated tokens. This logic must be implemented in pure Rust, iterating over the raw ![][image9] bytes logit allocation2. If ![][image11] represents a user-defined repetition penalty scalar greater than 1.0, the runtime must identify all token IDs currently present in the active transcript. For each identified token, if its raw logit value is positive, it must be divided by ![][image11]. If the raw logit value is negative, it must be multiplied by ![][image11]. This calculation aggressively reduces the probability mass of recurring tokens before the softmax or top-k filtering is applied, fundamentally resolving the statistical tendency for SLMs to collapse into localized loops.  
The third intervention involves enforcing explicit EOS parsing and loop termination logic. The runtime must programmatically define stop conditions outside of the hard context limit to prevent the generation of gibberish. The global Runtime state must permanently store the integer ID of the EOS token, as parsed directly from the BPE1 or BTOK metadata embedded in the SLM1 container4. Immediately following the PRNG candidate selection in the decoding loop, the chosen token ID must be evaluated. If the sampled ID exactly matches the EOS identifier, the autoregressive loop must execute a graceful break. Upon breaking, the runtime must finalize the generation transaction by capturing the elapsed time, recording the numeric code for success, and packaging these metrics into the diagnostic JSON payload before returning control across the ABI to the JavaScript shell2.  
Finally, the runtime must implement resilient UTF-8 boundary handling for the streaming output. The WASM presentation layer must be modified to include a transient byte buffer. As the autoregressive decoder emits token IDs, the corresponding raw bytes from the tokenizer dictionary must be appended to this buffer. The Rust code must actively monitor this buffer using standard UTF-8 validation functions (e.g., std::str::from\_utf8). The runtime must only flush the decoded string sequence to the browser interface when the buffer contains a complete, valid UTF-8 sequence, seamlessly holding partial multi-byte characters in memory until their constituent bytes are fully generated in subsequent passes.

## **Testable Acceptance Criteria**

To mathematically and systematically guarantee that the TinyRustLM execution path has successfully migrated from a deterministic smoke test harness to a viable inference engine, the engineering interventions must be verified against rigorous, narrative-driven testing protocols. These falsification tests are designed to execute directly within the browser's JavaScript test harness, asserting the correct behavior of the WebAssembly module without relying on external dependencies.  
**The RoPE and KV Indexing Assertion:** To validate the commit discipline, initialize a standard text prompt consisting of exactly 5 tokens. Command the runtime to generate exactly 10 additional tokens. Upon completion, halt the runtime and inspect the internal active\_seq\_len integer exposed via the diagnostic telemetry. The integer must read exactly 15\. Furthermore, memory inspection of the WASM heap must confirm that the RoPE kernel executed with the position index ![][image12] for the final generated token. The pre-allocated KV cache buffer, extending from offset 0 to the specific byte boundary of 15 \* head\_dim, must contain non-zero, continuously mutated floating-point data. Critically, the memory buffer extending beyond 15 \* head\_dim up to the context capacity limit must remain entirely untouched, mathematically proving that the pointer discipline successfully prevented unbounded cache corruption.  
**The Repetition Penalty Falsification:** To validate the penalty logic, the tester must override the loaded model weights with a custom SLM1 fixture specifically engineered to yield a perfectly uniform, flat logit distribution across the entire vocabulary space for all possible inputs. Set the repetition penalty scalar ![][image11] to an aggressive value, such as 1.5, and initialize generation. The core criterion is that the generated sequence must contain exactly zero repeated tokens within the active context window. Because the baseline distribution is perfectly flat, the generation of a token must cause its subsequent probability mass to mathematically collapse under the penalty application, forcing the PRNG to deterministically select a novel, unpenalized token ID on every single subsequent pass.  
**The UTF-8 Boundary Resolution Test:** This test ensures the presentation layer does not emit fragmented text. Manually configure the PRNG state in the test harness to deterministically select the four distinct constituent byte tokens of a 4-byte UTF-8 emoji sequentially over four distinct forward passes. The acceptance criterion demands that the WASM presentation layer must not emit a Unicode replacement character at any point during this sequence. The JavaScript application shell must register silence for the first three generation steps, only flushing the complete, visually accurate emoji to the frontend upon the receipt and mathematical validation of the final contiguous byte on the fourth step.  
**The EOS Halt Verification:** To guarantee the model respects semantic boundaries, inject the exact integer ID of the End-of-Sentence token directly into the start of the sampling candidate array, artificially granting it the highest probability mass before the PRNG selection phase. The generate() function must execute exactly one forward pass, sample the injected EOS token, and immediately terminate the autoregressive loop. The context length must increase by exactly 1\. The execution loop must not continue computing forward passes until the context capacity limit is reached, and no infinite WebAssembly execution traps may be triggered in the host browser.  
**The Multi-Turn Memory Safety Audit:** To ensure the context reset protocol is functioning as a soft-reset rather than a destructive deallocation, perform 50 rapid, successive context resets and prompt prefill transactions in a tight automated loop. The host browser's performance monitor must indicate absolutely zero increase in the active memory footprint after the initial 128 MiB .slm load transaction. The WASM linear memory must remain strictly bounded by the initial pre-allocated tensor and scratch footprint, proving that the active\_seq\_len pointer is correctly zeroing out without leaking memory or triggering expensive garbage collection routines.

## **Suggested Diagnostic Telemetry**

To facilitate the rapid debugging of these complex autoregressive pipelines and to support the broader TinyRustLM community, the runtime must leverage its existing presentation separation layer to emit highly granular telemetry. The Runtime diagnostics JSON schema4 should be expanded to include the following keys and data structures, packaged safely over the WASM boundary to the JavaScript shell immediately after every generation transaction concludes2.

| JSON Telemetry Key | Data Type | Diagnostic Purpose |
| :---- | :---- | :---- |
| active\_sequence\_length | Integer | Tracks the true offset of the KV cache pointer at the end of generation. This immediately exposes systemic failures in the commit discipline or context pointer resets. |
| rope\_theta\_applied | Float | Verifies that offset 56 from the SLM1 binary header was successfully parsed and injected into the attention kernels, confirming positional stability. |
| sampling\_entropy | Float | Measures the Shannon entropy of the top 10 logits prior to candidate selection. A value approaching ![][image13] on untrained weights indicates a catastrophic math failure in the forward pass arrays. |
| repetition\_penalty\_active | Boolean | Confirms whether the scalar penalty ![][image11] was actively applied to the transcript vector during the transaction, aiding in tuning behavioral biases. |
| prng\_state\_hash | String | A cryptographic or non-cryptographic hash of the internal PRNG state post-generation. Proves whether the deterministic seed is successfully mutating across token steps or if the generator has stalled. |
| eos\_token\_id\_parsed | Integer | Validates that the BPE1 or BTOK dictionary correctly identified the vocabulary boundary marker, essential for debugging models that refuse to halt. |
| kv\_cache\_utilization | String (Percentage) | Calculated as active\_sequence\_length / context\_capacity. Exposes how close the model is to triggering an out-of-bounds memory trap or requiring an eviction strategy. |

The transformation of TinyRustLM from an experimental evaluation harness parsing fixture weights into a genuinely coherent, browser-local generation engine requires profound and precise modifications to its autoregressive state machine. The observed limitations—most notably the tendency toward endless repetition loops and fragmented tokenization—are not inherent flaws of WebAssembly execution or the Rust language. Rather, they are direct symptoms of incomplete context pointer management, stationary positional embeddings, unpenalized uniform sampling, and rigid EOS handling. By rigidly enforcing KV cache commit disciplines, implementing standard mathematical repetition penalties, establishing robust UTF-8 boundary streaming, and properly managing the PRNG state mutation within the strict 128 MiB memory envelope, the runtime can successfully decouple context capacity from sequence progression and achieve a state of coherent, reliable local intelligence.
